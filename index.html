# Pharmamandu Dot Com Pvt. Ltd. — Field Sales & Distribution System ### Build Specification for Development Team **Prepared for:** Pharmamandu Dot Com Pvt. Ltd., Harisiddhi-28, Lalitpur **Domain:** www.pharmamandu.com **Document purpose:** hand-off spec so a developer/agency can scope, quote, and build the production system. Pairs with the interactive prototype (`pharmamandu-prototype.jsx`). --- ## 1. System overview A web application (with a companion mobile app for field staff) that manages the sales hierarchy, targets, orders, doctor-level sales tracking, cash collection, and GPS location for Pharmamandu's field force. **Not a marketing website** — this is an internal operations system. A separate small public site (company info + contact) can be built later if needed, but is out of scope here. ## 2. User roles & permissions | Role | Sees | Can do | |---|---|---| | **Country Manager** | All regions, all data | Create any profile, set targets at any level, view all reports | | **Regional Manager** | Their region only | Create Area/MR profiles under them, set targets for their region, view regional reports | | **Area Sales Manager** | Their area only | Create MR profiles under them, set MR targets, view area reports | | **Marketing Representative (MR)** | Own data only | Log doctor visits & sales, place orders, log cash collection, log location check-ins | Each role only sees data belonging to itself and the roles below it in the hierarchy (roll-up reporting), never lateral or upward data outside their chain. ## 3. Core modules 1. **Authentication** — Gmail-based sign-up/login with OTP email verification (no self-service password reset bypass; admin can force re-verification). A view-only **guest sign-in** path lets someone preview any role's console without an account, with all create/edit actions disabled. 2. **Admin panel** — create/edit/deactivate user profiles; assign manager relationships; assign region/area. 3. **Target management** — set Monthly / Quarterly / Yearly targets per user; quarterly and yearly can either be entered directly or auto-computed as a multiple of the monthly figure (business decision needed — see Open Questions). 4. **Master data management** — a single admin area to maintain the three shared lists everyone else picks from: - **Products & divisions** (e.g. Cap. Cyto-Min, Cap. Cyto-12, Tab. Cyto-Cal, Tab. Multiplat, Protein. Cyto.Pro, Radiosoothe Ointment, Radiosoothe Oro Spray) - **Hospitals to visit** (e.g. Nepal Cancer Hospital, Ohm Hospital, Bhaktapur Cancer Hospital, Neorvic Hospital, Helios Hospital, National Cancer Hospital) - **Prescriber roster** (doctor name, hospital, assigned MR) 5. **Order management** — MR raises an order against the company or a named stockist; status flow: Pending → Approved → Dispatched → Delivered; manager gets notified on new orders. 6. **Doctor & sales tracking** — log product-wise sales value against a prescriber per month, drawing from the shared prescriber roster. 7. **Daily visit reporting** — MR submits a same-day visit record (doctor seen, hospital, notes) from the field; Country/Regional/Area panels see a rolled-up visit log with a weekly visit-count per MR, used alongside sales figures as a performance signal. 8. **Cash collection** — MR logs cash collected (amount, date, note); rolls up into daily/monthly collection reports per MR, area, region, country. 9. **Location tracking** — mobile app pushes periodic GPS check-ins; web console shows last-known location and a visit log per MR on a map. 10. **Sales dashboards** — target vs achieved at every hierarchy level, for monthly/quarterly/yearly periods; MR-to-MR comparison; doctor-wise contribution. 11. **Chatbot** — in-app assistant answering common questions (target status, how to place an order, how to log a visit) — v1 can be rule-based/FAQ; v2 can add an LLM backend for natural-language queries against the user's own data. ## 4. Suggested tech stack - **Frontend (web):** React + Tailwind, deployed as a single-page app. - **Mobile app (MR field app):** React Native or Flutter — needed for background GPS and offline-friendly order/doctor logging. - **Backend:** Node.js (NestJS/Express) or Django REST Framework — either is fine; choose based on the developer's strength. - **Database:** PostgreSQL (relational data — users, hierarchy, targets, orders, doctors, sales, cash — all relational). - **Auth:** Google OAuth for Gmail sign-in + email OTP as a second factor. - **Maps/Location:** Google Maps Platform (Geocoding + Maps SDK) for the mobile check-ins and the web location dashboard. - **Notifications:** Email (order/target alerts) via a transactional email provider; optional SMS for stockists without email. - **Hosting:** any standard cloud VM/App-Service setup; a managed Postgres instance; domain already owned (pharmamandu.com) just needs DNS pointed at the host. ## 5. Data model (high level) ``` User - id, name, email, gmail_verified, role (country/regional/area/mr) - region, area, manager_id (self-referencing FK) - created_at, active Target - id, user_id, period_type (monthly/quarterly/yearly), period_value, amount Product - id, name, division Order - id, mr_id, product_id, qty, destination_type (company/stockist), destination_name, status, created_at Doctor - id, name, hospital, area, mr_id DoctorSale - id, doctor_id, product_id, value, month CashCollection - id, mr_id, amount, note, date LocationPing - id, mr_id, latitude, longitude, timestamp, status_label Hospital - id, name DailyVisit - id, mr_id, date, doctor_id, hospital, notes ``` ## 6. Reporting requirements - Sales vs target, per user, for **monthly, quarterly, and yearly** periods. - MR-wise comparison (bar chart), filterable by period, area, region. - Doctor-wise sales, filterable by month/quarter/year. - Cash collection totals, filterable by MR / area / region / date range. - Roll-up view showing the four-tier hierarchy with achievement % at each tier. ## 7. Open questions for Pharmamandu to decide before development starts 1. Should quarterly/yearly targets be entered independently, or always calculated from the monthly figure (e.g., quarterly = 3× monthly)? 2. Should Area Sales Managers be able to edit targets themselves, or only view/propose them for Regional Manager approval? 3. Stockist list — is there an existing list of stockists to import, or should the admin panel manage that as a new module (Stockist Directory)? 4. Location tracking — is continuous background GPS required, or is a check-in at each doctor/pharmacy visit sufficient? (This affects battery life and privacy disclosure requirements for staff.) 5. Chatbot — is a simple FAQ bot acceptable for v1, or is natural-language querying of personal sales data ("what's my target this month") required from day one? 6. Order approval — does an order need Area Manager sign-off before it reaches the company/stockist, or can MRs submit directly? ## 8. Suggested phased delivery | Phase | Scope | Rough duration | |---|---|---| | 1 | Auth, admin panel, hierarchy, targets, products | 3–4 weeks | | 2 | Orders, doctors & sales logging, cash collection (web only) | 3–4 weeks | | 3 | Dashboards & MR comparison reporting | 2 weeks | | 4 | Mobile app (MR field app) with GPS check-ins | 4–5 weeks | | 5 | Chatbot v1, polish, UAT, launch on www.pharmamandu.com | 2 weeks | *(Durations assume a small dedicated team of 2–3 developers; adjust based on who is actually hired.)* ## 9. Reference An interactive prototype (`pharmamandu-prototype.jsx`) demonstrates all four role panels, the admin flows, order/doctor/cash entry, MR comparison charts, a location tracking view, Gmail OTP login flow, and a chatbot widget, using sample data — use it to validate the intended UX with your team before development begins.
